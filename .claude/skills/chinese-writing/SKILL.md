# 中文技術寫作

這份 skill 描述本 repo 的中文寫法。適用於 PR 描述、commit 訊息、`docs/` 下的設計文件與計畫、README、以及對使用者的回覆。

判準只有一個：**沒有跟過這段流程的人，讀一次就懂。** 寫給自己看的筆記不算合格。

範例對照見 `references/examples.md`。裡面用本 repo 真實的 PR 描述，標出哪些讀得懂、哪些讀不懂、差在哪。

## 句子

- 一句只講一件事：誰、做了什麼、結果是什麼。每句用句號結尾。
- 一句裡不放第二個動作。要講第二件事就另起一句。
- 主詞和受詞要是短名詞。不用「的」串三層以上修飾語。修飾語裡若藏了動作（「綁錯欄的 NaN」），把那個動作拆成自己的句子。
- 不用「——」接兩個子句。它讓讀者猜關係（因為？所以？例如？）。用「因為」「所以」「例如」直接寫出來。「：」「；」「→」用來排並列或先後的項目可以，每一項要是完整的事實。
- 括號只放短補充（版本號、檔名、數量、一句說明）。括號裡不放清單，不套第二層括號。
- 每個 bullet 都是完整句子，有主詞有動詞。不寫名詞堆疊。
  - 不好：「versionId 一律不可逆摘要」
  - 好：「versionId 一律用不可逆摘要，模型讀不出原始路徑。」

## 用詞

- 不用比喻代替描述。下面這些詞一律換成實際發生的動作：

  | 比喻 | 換成 |
  |---|---|
  | 退場、退役、退貨 | 拿掉、刪除、不再呼叫 |
  | 兜底 | 最後由 X 處理 |
  | 釘死、釘住 | 有測試確認 |
  | 爆掉、炸掉 | 會拋錯、頁面顯示錯誤 |
  | 斷裂、斷了 | 沒有人再寫入、沒有人再呼叫 |
  | 接縫 | 可替換的介面、由 internal 覆寫的檔案 |
  | 分歧 | 兩邊各自維護一份 |
  | 真相來源 | 唯一設定處 |
  | 空轉 | 呼叫了但沒有結果 |
  | 外洩 | 出現在 log 或 repo 裡 |

- 專案自創的詞第一次出現時，用一句白話解釋它是什麼。解釋裡不能再出現其他專案自創詞。
- 程式名稱（函式、檔案、參數）後面接一句它做什麼，不讓名稱自己撐句子。
  - 不好：「`getCol` 全鏈退場」
  - 好：「`getCol` 是用欄位序號讀值的函式。已全部刪除，改用欄位名稱讀值。」
- 符號縮寫可以用（60→180s、9/9、+2 測試），但只用在數字與計數，不用來接句子。
- 中英夾雜可以。檔名、指令、程式名稱、既有英文術語保留英文。

## 結構

- 順序照讀者需要，不照 commit 順序或時間順序：
  1. 背景：現在的問題、它造成什麼後果、所以這個 PR 怎麼做。每一點三句。
  2. 這個 PR 做什麼。
  3. 為什麼會這樣（根因）。
  4. 改了什麼。
  5. 副作用。每一點寫改了什麼，以及為什麼可以接受。
  6. 怎麼驗證。
  7. 要留意什麼。
- 撐起整份文件的那個詞單獨一段定義：它是什麼、在產品裡對應什麼、在這個 PR 裡由什麼代替。定義完寫一句「下文的 X 都指這個」。
- 有時間先後或階段的流程，先命名階段，再在每一節說明自己屬於哪個階段。圖裡直接標出「未實作」「不在本 PR」。
- 一組有多個欄位的項目用表格，不用括號或分號塞進一句。
- 表格的每個欄位名都是讀者會問的問題：為什麼、誰能動作、看什麼。
- 用等級（高中低、P0/P1）之前先定義每一級「出錯會怎樣」。
- 粗體只用在給讀者的指示（「不要看整個 diff」「從這個檔開始」）。不粗體結論、口號、原則。
- 描述，不說服。寫發生了什麼與為什麼這樣選；不寫格言，不寫「正確答案是…」。
- 不同用途的內容分開段落：實驗紀錄、部署注意、審查結論各自一段，不混在同一節。
- 提到的檔案與文件一律附連結（PR 描述用 GitHub 連結，repo 內文件用相對路徑）。
- 留意事項若牽涉未完成的部分，寫出怎麼關掉它。
