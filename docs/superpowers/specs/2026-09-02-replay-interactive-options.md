# 分享頁互動方案：B 案 vs C 案（白話版）

> 狀態：討論紀錄（2026-09-02），尚未定案。本文把「分享出去的 dashboard 要不要能互動、怎麼做」的
> 幾條路線用白話寫清楚，供決策與交接。正式契約以主 spec（2026-08-30-mcp-datasource-design.md）為準。

## 一、我們在解什麼問題

現在的流程：使用者在對話中選好 API 資料源（connector）→ agent 拉資料、跑 SQL、
產出一頁 dashboard。這頁 dashboard 的數字是**寫死的**——產出當下算好、塞進 HTML 裡。

想要的下一步有兩層：

1. **分享**：把 dashboard 分享給同事，同事打開時要看到「他自己權限內的、當下最新的」資料，
   不是 owner 發布當時的舊數字。
2. **頁面互動**：打開的人可以在頁面上改條件——例如有個下拉選單選 fab、按個「重新整理」——
   不用回到對話裡重新問。

第 1 層已經定案叫 **V1**（開頁時後端整頁重算一次，頁面本身沒有任何按鈕），做法簡單、先做。
本文討論的是第 2 層：頁面互動要怎麼做，有 B、C 兩條路。

## 二、兩案一句話

- **C 案**：頁面上有選單，但按下去之後是「請後端重算一次」——算數字的還是後端那套 SQL。
- **B 案**：頁面自己就是一支完整的小程式——自己打 API 拿資料、自己用 JS 算數字、自己畫圖。
  （參考對象：Claude Artifact 的 MCP 頁面就是這樣運作的。）

兩案共用同一個底座：dashboard 都關在 sandbox iframe 裡、不准直接連網，
唯一的出口是傳訊息給外層頁面（postMessage），由外層代打 API。
發布時會凍結一份「這頁准用哪些工具」的白名單，超出白名單的呼叫一律擋掉。

## 三、C 案：頁面有選單、後端算數字

### 打開分享頁時發生什麼

1. 瀏覽器載入凍結的 HTML（裡面有一個空的 fab 下拉選單）
2. 頁面裡我們預先塞好的一段固定程式（runtime）啟動，向外層要兩樣東西：
   - 「fab 選單的選項」→ 後端幫忙打 `list_fabs`（用**開頁者**的帳號），拿到他有權看的 fab 清單
   - 「算好的數字」→ 後端照發布時凍結的配方重跑一遍：
     用一樣的參數重新拉資料 → 重新跑當初那幾條 SQL → 把結果傳回頁面
3. runtime 把數字塞進圖表、把選項塞進選單，頁面亮起來

### 改選單時發生什麼

選 FAB_C → runtime 跟外層說「fab 換成 FAB_C 再算一次」→ 後端把凍結配方裡的 fab 參數
換掉、重拉重算 → 新數字傳回來 → 圖表原地重畫（不重新載入頁面）。

### 要蓋的東西

- 後端：重算端點（拉資料＋跑 SQL＋回結果）、代打 API 的轉發層、白名單檢查
- 頁面：那段固定 runtime（填選單、畫 loading、錯誤提示、防連點——寫一次全部頁面共用）
- 模型端：產 dashboard 時多兩個小要求——圖表畫在一個可以重複呼叫的函式裡、
  選單用固定格式的標記宣告（「這個選單的選項來自 list_fabs、值取 id 欄」）

### 優點

- **數字永遠對**：算的人始終是同一套 SQL，對話裡說的跟頁面顯示的是同一個來源
- **好維護**：邏輯全在我們寫的程式裡。runtime 有 bug 修一次，所有已發布的頁面自動吃到修復，
  不用重新生成任何 dashboard
- 模型只需要做很簡單的事，現在的模型（deepseek-v4-flash）做得到

### 缺點

- 每次改選單要等後端重算（1～3 秒）
- **互動能力是「型錄式」的**：我們支援什麼互動、頁面才有什麼互動。
  今天支援單層下拉選單；哪天想要「選了 fab 之後、週別選項跟著變」（連動選單），
  就要回來擴充宣告格式、改 runtime、改檢查——每個新花樣都是一次平台工程。

## 四、B 案：頁面自己抓、自己算

### 打開分享頁時發生什麼

1. 瀏覽器載入 HTML——裡面是模型生成的一支完整 JS 程式
2. 這支 JS 自己透過外層代打 API：先打 `list_fabs` 填選單、再打 `get_quality` 拿原始資料
3. 拿到原始資料後，**JS 自己算**平均良率、分組、趨勢，自己畫圖

### 改選單時發生什麼

JS 自己處理：重打一次 API（或用快取）、重算、重畫。要做連動選單、自動重新整理、
「失敗時保留上一份資料」這些花樣，都只是 JS 多寫幾行——不需要動平台。

### 要蓋的東西

- 後端：只要一個很薄的「代打 API」端點＋白名單檢查（比 C 少一半以上）
- 模型端：**整套生成方式重寫**——從「產一頁讀現成數字的版面」變成
  「產一支會抓資料、算數字、處理錯誤的完整程式」

### 優點

- 互動體驗最好、最自由：模型想給頁面什麼功能都行，平台不用跟著改
- 後端要蓋的東西最少

### 缺點（兩個都很重）

1. **模型寫得出來嗎？** 參考範例（Claude 的 Gmail 頁面）是前沿模型寫的：
   分頁抓取、快取時間戳、錯誤分級、防止舊請求蓋掉新畫面……這種品質的 JS，
   我們的模型能不能穩定產出，是未知數。
2. **算錯了很難救**：每一頁的計算邏輯都是那一頁自己的 JS。
   算錯＝bug 凍在那個 artifact 裡，不能集中修，只能重新生成那一頁。
   「數字不對」的客訴要一頁一頁進去看各自不同的 JS。

### B 案的補救：發布前「對賬」

B 最大的風險是「對話裡用 SQL 算的」跟「頁面上用 JS 算的」不一致。
但發布時我們手上剛好有兩樣東西：**當初拉回來的原始資料**（存檔了）和
**SQL 算出的正確答案**（也存檔了）。所以可以自動改考卷：

```
發布前：
  1. 在無頭瀏覽器裡打開生成的頁面
  2. 把「代打 API」接到存檔的原始資料上（不打真 API，餵當初那份）
  3. 讓頁面的 JS 算一遍，把算出來的數字交出來
  4. 跟 SQL 的正確答案逐項比對
  5. 全對 → 准發布；不對 → 把差異丟回給模型修，修到對為止
```

通過對賬的頁面，邏輯就是驗證過的。上線後如果頁面數字跟對話不同，
可以放心說「那是資料變新了」而不是「算錯了」。

配套要求：頁面每張圖要標注「我對應對話裡的哪條查詢」（讓考卷有標準答案可對）、
頁面要顯示「資料讀取時間」（讓大家知道數字是即時的、跟對話快照本來就會不同）。

## 五、比較表

| | C 案 | B 案 |
|---|---|---|
| 數字正確性 | SQL 單一來源，天生一致 | 靠發布前對賬把關 |
| 對模型的要求 | 低（現有模型可） | 高（需要實驗驗證） |
| 改選單的速度 | 等後端 1～3 秒 | 幾乎即時 |
| 互動自由度 | 我們支援什麼才有什麼 | 模型想寫什麼都行 |
| 出 bug 時 | 修我們的程式，一次全好 | 一頁一頁重新生成 |
| 後端工程量 | 較多 | 較少 |
| 長期維護 | 都是自己人的確定性程式 | 跟模型品質長期拉鋸 |

兩案**不相容**：C 的頁面讀後端算好的數字，B 的頁面自己算——
選了一邊再換，已發布的頁面要全部重新生成，C 專屬的建設（重算端點、宣告格式、runtime 的大半）會報廢。

## 六、目前的建議（未定案）

1. **V1 先做**（開頁重算、無互動）——它是原始分享需求的完整解，
   而且不管之後選 B 還是 C 都不白蓋（材料存檔、重算端點兩案都用得到或只小改）。
2. **B 的可行性先用實驗驗**——不用蓋任何基建：讓模型試產五個「自己抓自己算」的頁面，
   拿測試資料對答案，看良率。這個實驗台跟「對賬」是同一套東西，蓋一次兩用。
3. 實驗結果出來再選：良率能看 → 走 B（省掉 C 的大半工程）；
   良率不行 → 走 C，並且把互動範圍刻意壓在「簡單選單」，更花的互動請使用者回對話問 agent。

## 七、名詞小抄

- **connector**：一個 API 資料源（對應一台 MCP server），例如「品質資料」
- **lookup**：拿選項用的查詢（例如 `list_fabs` 列出有哪些 fab），資料不落表
- **落表（land_as）**：把 API 回應存成 DuckDB 表，讓 agent 可以下 SQL
- **凍結配方**：發布時存下來的「當初用什麼參數拉了哪些資料＋跑了哪些 SQL」，重算時照著做
- **橋（bridge）**：sandbox 頁面跟外層之間唯一的通話管道（postMessage），外層代打 API
- **白名單（capabilities）**：發布時凍結的「這頁准用哪些工具」清單
- **對賬**：發布前用存檔資料讓頁面 JS 算一遍、跟 SQL 答案比對的自動驗證
